## 逐项证据

### 1. ⌘R 重复启动

21:07:29 启动；Core 在 21:07:31.757 追加 task 3，21:07:31.776 开始。原生 AX 在 21:07:35.286 观察到“停止”和 StartUp 正在执行；随后连续按三次 ⌘R，21:07:35.467 完成输入。Core 在 21:07:36.292 自然发出 AllTasksCompleted，GUI 显示“任务已全部完成”并恢复“开始”。该窗口没有第二次 append/start，也没有 stop。

较早的 21:04:59 连续启动输入也仅产生 task 2；这轮从空闲开始，不能用它代替上述已明确观察到运行中状态的用例。

### 2. 启动期间停止及重试

21:04:36 连续发出 ⌘R、⌘.；持久 GUI 日志先记录“当前正在启动或停止任务，请稍后重试。”，随后连接成功，task 1 正常运行并完成。停止没有被排队。

21:08:19 再次执行启动期停止；21:08:21.671 开始 task 4。启动结束后再次发出 ⌘.，Core 在 21:08:25.268 收到 stop，21:08:26.350 发出 TaskChainStopped；GUI 持久日志显示“已停止”，后续原生 AX 观察到“开始”并成功启动 task 5。

**未通过的反馈项：** 21:04:39 的原生日志列表已经没有此前忙碌提示，只剩连接和运行信息。源码中 `beginTaskOperation()` 在拒绝时调用 logError，而 `ensureHandle()` 的异步准备完成后调用 `logStore.clearLogs()`；`NewViewModel.clearLogs()` 清空界面数组，持久文件保留该提示。这里仅记录缺口，没有将其写成已修复。

**后续修复：** 评审修复轮已将清空上一会话日志的时机移入 `beginTaskOperation()` 准入（先记录会话边界，核心运行复核通过、未被取消后才清除准入前的旧条目，被拒路径不清空任何日志），并为自动停止增加静默参数；本段的"未通过"记录保留为修复前时点的证据。

### 3. 短任务完成与空队列快速收尾

真实 StartUp task 5 在 21:10:21.842 开始、21:10:27.383 完成；观察到“开始”后，在同一原生操作调用内 22ms 后再次按 ⌘R，task 6 随后成功开始并完成。22ms 是从 AX 观察完成状态到发出键盘输入的间隔，不能解释为距 Core 实际完成仅 22ms。

21:11:58 起通过 GUI 关闭全部任务并启动真实空队列；21:12:00.456 的 Core start 调用记录为 0ms 返回，原生 AX 显示“开始”。立即再次通过 GUI 启动，21:12:04.913 的 start 调用同样记录 0ms 返回，AX 再次显示“开始”。没有追加任务或产生任务链回调，符合该 Core 空队列路径。0ms 指 start API 调用耗时，没有测量整个 Core 运行生命周期。

这补充了真实 Core 快速归空闲及可重启证据；精确的“完成回调先于 await 恢复”、旧回调延迟及私有计时元数据仍以已有 305 项可控时序断言为证，本轮没有声称强制复现每一种竞争时序。

### 4. 定时器实际失败与恢复

通过原生定时配置创建并启用 21:14 定时器，未修改系统时钟。故障条件为独立实例的无效连接地址 `127.0.0.165432`。Core 在 21:14:00.174 发出 ConnectFailed，原因为目标设备不存在；界面显示 `StartTasksFailed: connectFailed`、检查连接设置提示和“开始”按钮。

同一个定时器的实际控制台输出：

```text
Timer 98DCB0BD-0E98-47C0-B84A-AE2E8C706D72-21-14 is scheduled at 2026年10月29日 星期四 中国标准时间21:14:00
Failed to start scheduled daily task. Timer id: 98DCB0BD-0E98-47C0-B84A-AE2E8C706D72
```

没有对应的 Skip 或成功启动输出。此处验证的是连接失败分支；真实 Core start 返回失败的定时分支仍只有前轮模型测试证据。

关闭该定时器并恢复 `127.0.0.1:5555` 后，21:15:27 开始 task 7，21:15:32 完成；原生 AX 和截图确认恢复“开始”。持久偏好核实定时器 isEnabled=false、连接地址正确，随后退出独立测试实例。游戏仍在主页。
